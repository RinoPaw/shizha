# 检索设计

本项目当前采用轻量三层检索方案，目标是兼顾稳定性、可解释性和后续扩展空间，而不是一开始就上重量级搜索系统。

## 设计目标

系统希望同时满足三件事：

1. 用户输入标准诈骗术语时，结果要稳定、直接、可解释。
2. 用户出现同音误写、拼音输入或输入法误选时，不要完全搜不到。
3. 用户不用数据集原词、但语义相关时，在开启 embedding 后仍有召回能力。

## 三层结构

### 1. 关键词检索

关键词检索是主路径，负责精确、可控、可解释的排序。

当前会综合以下文本来源：

- 标题
- `ccl2023_category`
- 摘要
- `content`
- `build_search_text()` 聚合字段

其中标题和类别权重更高，聚合字段权重更低，用来补充召回。

### 2. 拼音模糊兜底

拼音检索不是主排序核心，而是中文输入场景下的补充机制。

它主要解决：

- 同音误写
- 拼音输入
- 输入法误选

当前拼音索引基于：

- 标题
- `ccl2023_category`

并且只有在词法检索没有明显标题命中时，才会让拼音结果插到前面，避免把本来已经很清楚的结果打乱。

### 3. Embedding 语义召回

当开启 embedding 时，系统会额外做语义检索，用于覆盖表达差异。

适合的问题例如：

- “有人让我下载陌生软件然后说能赚钱”
- “假装警察说我银行卡有问题”

这类表达不一定直接命中数据集里的标准词，但在语义上可能对应：

- 刷单返利
- 冒充公检法
- 安全账户
- 陌生 App

## 当前流程

当前 `search_items()` 的整体流程是：

1. `normalize_search_query()`
2. `tokenize()`
3. `rank_lexical()`
4. 可选 `rank_hybrid()` 进行 lexical + semantic 融合
5. 过滤低分结果
6. `prepend_pinyin_matches()` 做拼音兜底
7. 分页返回

可以概括为：

- 无 embedding：`lexical -> pinyin fallback`
- 有 embedding：`lexical -> semantic fusion -> pinyin fallback`

## 为什么现在不直接上 Elasticsearch

当前数据量不大，本地运行优先，维护成本比绝对检索能力更重要。

因此现在优先保留：

- 简单 Python 词法检索
- 可选拼音兜底
- 可选 embedding 召回

这套结构已经足够支撑当前反诈案例库。

## 后续扩展路径

为了避免搜索规则写死在数据模型里，搜索文本拼装已经放在 `search.py` 的 `build_search_text()` 中，而不是 `CaseItem` 属性。

以后如果数据变大，可以把 `search.py` 这一层替换为：

- SQLite FTS
- Meilisearch
- 其他轻量索引系统

这样 `web.py` 和 `agent.py` 基本不需要大改。
